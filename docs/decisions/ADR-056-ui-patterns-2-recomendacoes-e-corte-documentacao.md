# ADR-056 — UI Patterns 2 como contrato de apresentação e corte orientado por evidência

- **Status:** aceita pelo responsável em 2026-11-13.
- **Escopo:** tema `aculta420_v2`, componentes SDC e suas integrações de apresentação Drupal.
- **Motivo:** a documentação do tema divergiu do código e o acúmulo de templates e instruções legadas dificulta compor o site com UI Suite.
- **Referências:** [recomendações oficiais UI Patterns 2](https://project.pages.drupalcode.org/ui_patterns/2-authors/2-best-practices/), [autoria de componentes](https://project.pages.drupalcode.org/ui_patterns/2-authors/0-authoring-a-component/), [presenter templates](https://project.pages.drupalcode.org/ui_patterns/1-users/5-presenter-templates/), [stories e Library](https://project.pages.drupalcode.org/ui_patterns/2-authors/1-stories-and-library/), [release UI Patterns](https://www.drupal.org/project/ui_patterns/releases).

## Decisão

1. SDC é o contrato visual do tema. Cada componente novo deve incluir schema, Twig, assets necessários e ao menos uma story descoberta pela UI Patterns Library. A UI Patterns Library é a fonte única para o catálogo de SDCs/stories. Por decisão posterior do responsável em 2026-11-13, `aculta_ui_library` foi removido por completo, inclusive a rota de compatibilidade; manter somente `ui_patterns_library`.
2. Props carregam dados simples, tipados e necessários à apresentação; slots recebem conteúdo renderizável do Drupal. Não passar render arrays por props, nem criar prop drilling para filhos/renderables que podem ser slots. Slots são opcionais e devem tolerar qualquer conteúdo renderizável; não testar tipo de prop em Twig nem aplicar filtros dependentes de estrutura a slots. Props obrigatórias devem ter fallback seguro no template. Manter slots independentes; não indexar uma lista de slots a partir de outra. Usar a prop type `links` para menus, breadcrumbs, links e paginação. Componentes permanecem independentes, usam variants para diferenças visuais do mesmo modelo (não props que imitam variants), declaram default funcional e preferem nomes de variants alinhados aos modificadores de markup. Evitar combinações de props impossíveis, IDs fixos e contexto Twig implícito.
3. Usar a integração UI Patterns correspondente somente quando necessária: Blocks para blocos configuráveis; Layouts para seções do Layout Builder; Field Formatters para campos; Views para row/style/display. A escolha de integração não transfere consulta, autorização, acesso, cache ou regras de conteúdo ao tema.
4. Preferir construtores de display do Drupal para entidades e Views. Um presenter template pode permanecer como adaptador leve quando não há construtor apropriado, por exemplo no shell da página ou em menus. Não converter templates mecanicamente em SDCs.
5. Os metadados devem usar nomes agnósticos ao negócio quando o componente for reutilizável; peças internas devem ser identificáveis como internas, agrupadas e com slots `expected` quando a API instalada suportar. Stories devem exemplificar estados úteis sem listas artificiais de renderables. Twig deve usar `attributes` no wrapper, loopar slots com proteção para renderable unitário/lista e ser lintado. `include()` explícito é a opção para dependências inevitáveis entre componentes.
6. O corte legado será orientado por consumidores comprovados no código e Config Sync. Documentação e roadmaps devem refletir o checkout antes de planejar remoções. Migrações ocorrerão em lotes revisáveis com critérios de saída, validação de acesso/cache e evidência de renderização.
7. O tema mantém um shell único e as cinco regiões declaradas atualmente. A opção e o template paralelo `classic`/`v2` estão removidos do código-fonte. O no-op temporário do hook de sugestões foi removido após rebuild do cache do Runtime em 2026-11-14; nenhuma variante permanece como configuração ou contrato do tema.

### Decisões de escopo confirmadas pelo responsável

- SDC sem consumidor será candidato a remoção somente se não estiver publicado/selecionável em UI Libraries, não tiver consumidor no código/configuração e não houver plano aprovado. SDCs que integrem UI Libraries são preservados. Todo item oferecido pelas UI Libraries deve ser implementado como SDC; itens não SDC devem ser convertidos ou retirados do catálogo. Todo SDC mantido e todo SDC novo recebe story.
- Renomear componentes somente quando representarem um conceito reutilizável cujo nome atual está preso a domínio. Respeitar referências persistidas; preparar migração/compatibilidade antes da mudança.
- O alvo é tentar remover todos os templates atuais. No corte revisado em 2026-11-14, 17 permanecem após migrações comprovadas para SDCs/UI Patterns e remoção de adapters sem consumidor. Primeiro procurar substituição por entity display, Layout Builder, Views, Field Formatter, Block ou SDC chamado pelo render array. Só permanecerá um presenter mínimo quando o Drupal/UI Patterns exigir o theme hook e não houver display builder equivalente. Não remover contratos Core/HTMX/Forms sem substituto funcional.
- **Revisão posterior (2026-11-13; estado conferido em 2026-11-14):** primeiro, catálogo e prévias próprias de blocos foram retirados de `aculta_ui_library`; depois, o responsável determinou remover o módulo e seu redirect. O Config Sync e o Runtime não habilitam o módulo, que já não possui código executável, rota ou gate próprio no checkout. Os documentos residuais foram removidos. A UI Patterns Library oficial permanece habilitada. O Runtime descobriu 148 SDCs antes da purga; a última descoberta registrada encontrou 145, antes de `reply-indent`; na fotografia daquele corte o checkout continha 146; o worktree atual tem 150 e requer nova descoberta/cache. Resta limpar uma chave órfã de `system.schema` no Runtime com backup e prova de restauração. O gate de contrato continua exigindo stories e que só a Library oficial esteja habilitada.

## Relação com decisões anteriores

Esta ADR complementa a decisão vigente de corte radical da ADR-054: especifica como aplicar as recomendações oficiais UI Patterns 2 e exige reconciliação documental antes de priorizar novos lotes. Trechos antigos dos planos que determinam shell paralelo ou homologação visual como pré-condição estão superados. Preserva Layout Builder nos displays compatíveis, as cinco regiões do shell, os contratos da ADR-053 e as fronteiras entre tema e Portal. Não autoriza importação de configuração, migração estrutural ou operação de Runtime.

### Complemento da pesquisa oficial e lacunas de contrato (2026-11-14)

Critérios conferidos nas recomendações de [boas práticas](https://project.pages.drupalcode.org/ui_patterns/2-authors/2-best-practices/), [autoria de componentes](https://project.pages.drupalcode.org/ui_patterns/2-authors/0-authoring-a-component/) e [stories e Library](https://project.pages.drupalcode.org/ui_patterns/2-authors/1-stories-and-library/): props representam dados tipados usados pela lógica visual; slots recebem renderables livres; componentes devem tolerar renderables unitários/listas e entradas vazias; defaults/fallbacks devem ser seguros; `variants` descrevem diferenças visuais do mesmo modelo. Em UI Patterns 2, `variants` é metadado que também gera uma prop string enum e recebe tratamento próprio no formulário; a migração deve preservar renderização SDC direta no Core. `tags`, `links`, `slots.expected` e metadados de variants enriquecem descoberta/configuração quando são úteis, mas sua ausência global não constitui defeito por si só.

Inventário atual do worktree (inclui SDCs ainda não rastreados): 150 componentes, 244 stories, 550 props de topo (todas com descrição), 714 nós de schema tipados (todos com descrição), 80 SDCs com 159 props obrigatórias, 13 props `variant` enum e 275 slots. Varredura lexical dos manifests e templates de componente: os 550 props de topo restantes têm referência literal no Twig do próprio SDC; isso encerra a triagem por prop sem referência, sem provar validade dos valores dos producers. Os quatro props URLs removidos de `forum-quote` estavam descritos; a contagem atual reflete a redução de cinco URLs porque `permalink_url`, `edit_url`, `delete_url`, `quote_url` e `reply_url` saíram juntos. Uma busca estática por nome encontrou uso em Twig de 154 antes de `delete-confirm`; esse componente novo já tem chamada produtiva em dois templates, então o inventário literal deve ser regenerado, não inferido por soma. `studio-calendar.active_filter` foi removido do schema, da story e do Composer; os asserts Kernel agora verificam o estado em `filters[].active`, fonte única da seleção visual. Treze SDCs têm prop `variant` string enum. Sete manifests agora declaram metadados oficiais `variants` (`badge`, `breadcrumb`, `button`, `card-cultural`, `dialog`, `icon`, `reaction-emoji`), mantendo o prop enum SDC equivalente para renderização direta no Core; nenhum manifest declara `tags` ou `links`, e nenhum slot declara `expected`. A revisão semântica dos 13 contratos (2026-11-14) separou variantes de apresentação de seletores de conteúdo/estrutura. **Metadados `variants` implementados**: `badge` (classe visual do selo), `breadcrumb` (superfície padrão/contextual), `button` (ênfase/estado da ação), `card-cultural` (composição padrão/compacta), `dialog` (painel padrão/tela cheia), `icon` (peso visual) e `reaction-emoji` (desenho plano/colorido). Todos mantêm o mesmo modelo de conteúdo e alteram apresentação. **Manter como props comuns**: `author-card` escolhe contexto e dados/rótulos; `donation-presentation` seleciona modos de conteúdo/fluxo; `forum-topic` escolhe teaser/composição completa; `layout-page` controla estrutura da página; `site-footer` seleciona conjuntos de conteúdo distintos; `wiki-entry` separa artigo completo de teaser. A implementação inicial acrescentou metadados oficiais aos sete candidatos, preservando o prop `variant` no schema SDC para render direto no Core. O annotator instalado sintetiza o prop de UI Patterns a partir de `variants` e sobrescreve a definição descoberta; por isso, os dois enums precisam permanecer alinhados, com labels e ordem/default compatíveis. O gate de schema agora exige enum SDC alinhado em ordem com as chaves `variants` e títulos para cada opção; os gates estáticos passaram após a implementação. Ainda faltam preview da Library e render direto no Runtime para verificar descoberta, labels, seleção e compatibilidade. P1 permanece em aberto para provar a descoberta e seleção dos sete metadados de variantes na Library/Runtime, revisar obrigatoriedades e defaults/estados vazios, e homologar os filtros/conversões de slots; não há justificativa para tornar todos os props opcionais ou acrescentar metadados uniformemente.

Varredura estática dos 275 slots declarados: todos têm título e descrição. Um filtro lexical apontou 16 slots; a triagem manual encontrou 11 usos que convertem/inspecionam conteúdo, quatro testes simples de presença (`heading.content` e os três slots de `profile-details`) e um falso positivo (`forum-quote.avatar_media`, porque `raw` aplica-se ao prop vizinho `avatar`). Os testes de presença não são automaticamente violações. O slot morto `forum-quote.reactions_slot` foi removido do manifest/story após a busca em código, Config Sync e Runtime sem referências; o SDC segue no catálogo com contrato limitado ao que o Twig renderiza. A revisão cruzada corrigiu os manifests de `forum-author-line.avatar` e `forum-quote.avatar`: ambos descrevem o quadro vazio que o SDC `avatar` deixa sem mídia.

**Revisão da hipótese sobre Twig blocks (2026-11-14):** a leitura inicial que classificou cinco SDCs como slots perdidos estava errada. UI Patterns Library usa o mesmo caminho: `TwigExtension::renderComponentStory()` cria `#type: component` com `#slots`, e `ComponentElementAlter` converte as stories. Os `{% embed %}` em `forum-comment` e `revista-listing` também sobrescrevem os blocks válidos. O validator de renderização do tema passou após alinhar a asserção de `avatar` ao contrato: 91 componentes renderizados, incluindo `author-card` com avatar via slot. Não migrar esses templates/callers apenas por usarem blocks ou por compatibilidade com a Library. Permanecem válidos os itens de auditoria de conteúdo de slots (conversões/filtros, stories e o slot potencialmente morto), além de verificação visual/configuração Runtime por fluxo.
