## Protocolo verificável por componente

1. **Metadados:** abrir o `.component.yml`, conferir schema Core suportado pela versão instalada, status, props (tipos, required, defaults, enums), slots e nomes correspondentes no Twig. Faltas devem ser registradas com caminho/linha, não presumidas.
2. **Template:** verificar escaping, semântica HTML, IDs determinísticos, ARIA, ações e fallback sem JavaScript; não introduzir queries, access checks ou construção de URLs em Twig. Confirmar que não há H1 duplicado em `context-header` / `wiki-entry`.
3. **Visual:** mapear CSS e JS locais, tokens `--aculta-*`, variáveis UI Styles e responsabilidades de Bootstrap; modos claro/escuro devem manter geometria idêntica. Identificar regras globais que afetem outros componentes.
4. **Stories:** confirmar arquivos `.story.yml` correspondentes, entradas aceitas no schema e casos determinísticos, sem dados reais/privados; story presente não implica validação no UI Patterns Library.
5. **Consumidores:** identificar renderização efetiva em Twig, PHP/render arrays, Views/config e UI Patterns; classificar `sem consumidor identificado` quando só há hipótese. Auditar cacheability/access em providers, não no tema.
6. **Classificação auditável:** usar `SDC-CONFORME-ESTÁTICO` somente após passar os itens 1–5; `SDC-PARCIAL` para inconformidades; `LEGADO-MIGRAR` para reutilização que ainda dependa de Twig não-SDC; `NÃO-REUTILIZAR` para incompatibilidade semântica; `RUNTIME-PASS` somente com testes reais registrados.

## Prioridades e decisões de reuso

| Ordem | Escopo | Decisão de execução |
| --- | --- | --- |
| P0 | Institution Bar + Domain Header | Manter globalmente em todos os purposes; nenhum contexto de página pode substituir, esconder ou duplicar o shell multidomínio. |
| P1 | `context-header` + `wiki-entry` | Validar ownership cirúrgico do H1, breadcrumbs, render arrays, cache e segundo consumidor real; não criar duplicata. |
| P1 | `context-tabs` + Studio | Preservar navegação por rotas, histórico, `aria-current`, fallback sem JS; não reaproveitar `product-tabs` como tabs de rotas. |
| P1 | `alerts-trigger`, `messenger-trigger`, `cart-offcanvas` | Validar overlays, foco, Escape, isolamento por purpose e race AJAX B5-02 sem reescrever a engine Bootstrap. |
| P2 | `empty-state` + `messenger-state` | Compartilhar apenas superfície SDC neutra; estados de domínio e permissões continuam nos providers; não unificar componentes sem prova. |
| P2 | `card`, `figure`, `quote`, `content-grid` | Conferir slots/variantes em consumidores reais antes de promover reuso Revista, Wiki, Fórum, Gallery e LMS. |
| P3 | Demais componentes | Auditar individualmente sem migração em lote, com ownership e evidência por consumidor. |

## Sequência incremental pós-inventário

- **B6-S1a:** completar leitura de cada um dos 41 pares metadata/Twig, stories e CSS; publicar tabela de findings por caminho, severidade e prova. Não declarar os 41 aprovados em bloco.
- **B6-S1b:** rastrear consumidores reais e dependências UI Patterns/UI Styles por código/config, marcar o que somente o Runtime esclarece.
- **B6-S2:** correções pequenas e independentes apenas em contratos objetivamente defeituosos; atualizar story, catálogo, changelog e docs no mesmo commit de cada alteração.
- **B6-R:** executar Core SDC/SDC Devel, UI Patterns Library, UI Styles, shell/purpose, H1, história AJAX, cache/access, 320/360/390/768/1024/1280/1440px, zoom 200–400%, teclado, AT e light/dark no homelab; registrar provas e falhas, nunca presumir PASS.

## Restrições operacionais

Nenhum novo componente será criado enquanto existir SDC conforme para o mesmo papel. É proibido reutilizar Twig legado isolado como padrão transversal; migrar para SDC/UI Suite quando houver consumidor real. O tema controla apresentação; Portal e subkernels controlam regras, autorização e cache. Trabalhar exclusivamente na PR #297 e não incluir arquivos de Fórum, LMS ou frentes paralelas neste commit documental.
